# DriveSense Flutter Library

This directory contains the Flutter app code for DriveSense. The app is built
around a small set of shared runtime state, service classes that talk to the
backend, Isar repositories for offline trip data, and UI pages/widgets.

## Directory Map

- `main.dart` starts Flutter, restores secure session state, opens Isar, and
  registers the app routes.
- `runtime_store.dart` is the in-memory session and selection store used by
  pages and services during one app process.
- `config/` keeps app constants such as API configuration, asset paths, colors,
  and shared request header builders.
- `exceptions/` contains domain-specific exceptions surfaced by trip flows.
- `model/` contains API and Isar data models. Files ending in `.g.dart` are
  generated by Isar and should be regenerated instead of edited manually.
- `pages/` contains route-level Flutter screens.
- `repository/` wraps local Isar persistence for active and completed trips.
- `services/` contains backend clients, token/session handling, trip tracking,
  sync, PDF generation, and profile/vehicle/group operations.
- `widgets/` contains reusable UI pieces used by pages.

## Session And Auth Flow

`TokenStorage` owns persistence of account, refresh, and selected profile
tokens in secure storage. `AuthHttpClient.restoreSession()` loads those values
into `RuntimeStore` on startup and refreshes the account token when possible.

Most backend calls should use the top-level functions exported by
`services/auth_http_client.dart` instead of `package:http` directly. Callers
request authenticated cookies through `RequestHeaders.authenticated()` or
`RequestHeaders.authenticatedJson()`. The client replaces stale cookie headers
with the latest tokens from `RuntimeStore`, refreshes account tokens before
expiry, and retries one time after a `401` if refresh succeeds.

Profile tokens are profile-scoped. Switching the active profile in
`RuntimeStore.setActiveProfile()` clears profile-owned data such as vehicles,
protocols, trips, and trip detail cache so data from one profile is not shown
under another.

## Trip Lifecycle

Trip recording is split into three layers:

- `TripTrackingService` reads GPS positions. On Android it uses
  `flutter_foreground_task` so recording can continue while the app is in the
  background. Other platforms use an in-process Geolocator stream.
- `TripSessionService` owns the user-facing trip state. It starts, pauses,
  resumes, stops, or aborts the active trip and persists the active draft after
  each accepted GPS point.
- `TripSyncService` saves finished trips locally first and then attempts backend
  upload. Failed uploads remain in Isar as unsynced rows for later retry.

The foreground-service path writes accepted points directly to Isar before
notifying the main isolate. `TripSessionService` treats those callbacks as
already persisted and reloads the active draft, while in-process callbacks are
written by the session service itself.

## Local Data Boundaries

Local trip data is account-scoped through `LocalAccountScope`. Repositories
return empty results when no account is active and reject writes that would move
a row between accounts. When a different account signs in on the same device,
`TokenStorage` clears local trip data before storing the new account token.

Completed trips use a stable `localId`:

- `local:<accountId>:<temporaryTripId>` while only the local draft exists.
- `server:<accountId>:<serverTripId>` after the backend assigns a permanent id.

This lets the app collapse local drafts and server-confirmed rows into one
visible trip in protocol tables.

## Documentation Notes

Prefer Dart `///` comments for public classes, methods, and non-obvious domain
rules. Inline `//` comments should explain local implementation constraints,
not restate the code. Generated Isar files should stay undocumented by hand.
